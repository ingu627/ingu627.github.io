# Tech Blog Diagrammer (ingu627.github.io)

이 저장소에는 Mermaid 렌더러가 없다. 구조·상태 전이·요청 흐름을 설명할 때 필요한 그림만 `assets/images/<category>/<slug>.webp`로 첨부한다(폭 ≤ 1400px, 파일 ≤ 150KB).

## 1. 공식 원본 우선

1. 해당 글의 **실제 주장과 같은 범위**를 설명하는 공식 문서·논문·프로젝트의 도식을 먼저 찾는다. 도식이 글의 제품, 버전, 방향, 수치와 다르면 단지 공식이라는 이유로 쓰지 않는다.
2. **그 이미지 파일 자체**의 재배포·형식 변환 허가, 제3자 구성 요소와 상표 조건을 확인한다. 출처 표시만으로 허가가 생기지 않으며, Microsoft Learn 이미지 전체가 CC BY라고 가정하지 않는다.
3. 허가와 적합성이 확인되면 `official-<slug>.webp`로 변환한다. 캡션에는 저작자, 원문과 허가 근거, 라이선스, 리사이즈·형식 변환 여부를 적는다.
4. 적합한 원본이나 명시적 허가를 확인하지 못하면 이미지를 복제·핫링크하지 않는다. 내용을 이해한 뒤 별도의 구조도를 만들고, 확인하지 못한 라이선스는 보고한다.
5. 관련 없는 기존 자산은 지우지 않는다. 공유 자산을 교체할 때는 다른 글의 참조를 보존한다.

## 2. 전달할 관계를 먼저 설계

그림 하나가 답할 질문과 독자를 정하고, 검증된 구성 요소·경계·상태와 그 사이의 관계를 본문과 1차 출처에서 추출한다. 문장과 연결되지 않는 요소는 넣지 않는다. **관계가 없는 항목에는 화살표를 넣지 않는다.** 대안 비교는 순차 화살표 대신 나란한 분기와 같은 입력을 쓴다.

색만으로 의미를 전달하지 않고 범례나 직접 레이블을 쓴다. 실제로 측정하지 않은 곡선·수치·성능 우위를 그리지 않는다. 가정·예시와 실측을 구분하고 복잡한 그림은 주제별로 나눈다. 자세한 형식 선택은 [도식 설계 및 라이선스 가이드](references/diagram-prompts.md)를 따른다.

## 3. 제작 또는 원본 최적화

적합한 원본이 없으면 검증된 노드와 간선을 바탕으로 독립 도식을 만든다. 정확한 한글과 선·표식이 중요할 때는 SVG 같은 결정적 벡터 방식으로 배치하고 WebP로 내보낸다. 이미지 생성 모델을 쓸 때도 결과의 글자·관계·수치를 독립적으로 검수하고, 실패하면 재생성하거나 벡터 방식으로 다시 만든다.

`scripts/make_diagram.py`는 Python 표준 라이브러리와 별도 설치가 필요한 `Pillow`를 쓴다. Gemini 생성에는 네트워크와 API 키가 필요하다. `optimize`는 PNG/JPEG/SVG를 1400px 이하 WebP(`quality=85`, 150KB 이하 목표)로 저장한다.

```bash
# 공식 원본 또는 제작한 PNG/SVG를 규격 WebP로 저장
python3 .agents/skills/tech-blog-diagrammer/scripts/make_diagram.py optimize \
  /path/to/source.png \
  --category cloud \
  --slug official-example \
  --alt "Azure VNet과 Private Endpoint의 요청 경계"

# 이미지 모델로 초안을 만들 때만 (API 키 필요)
python3 .agents/skills/tech-blog-diagrammer/scripts/make_diagram.py generate \
  --category cloud \
  --slug example-flow \
  --prompt "wide 16:9, ..."
```

- 원본에 없는 수치, 제품 기능, 로고, 출처를 생성 모델이 넣지 않게 한다. 원본을 참고해 새로 그리더라도 구성과 표현을 그대로 복제하지 않는다.
- SVG는 래스터화 도구로 먼저 PNG로 바꾼 뒤 `optimize`에 전달한다. API 키가 없으면 허가된 공식 자료나 독립 벡터 도식을 쓰며 가짜 대체 이미지를 만들지 않는다.

## 4. 시각·기술 검수

원본과 최종 WebP를 `read`로 열어 보고, 글에 넣은 뒤 실제 브라우저에서 데스크톱과 약 390px 모바일 폭을 확인한다.

1. **정확성**: 각 노드·화살표 방향·경계·상태가 본문과 1차 출처를 따르는가? 비교 대상이 잘못된 실행 순서로 이어지지 않는가?
2. **문자와 시각 요소**: 한글·영문·수치에 오류, 겹침, 잘림이 없는가? 의미 없는 박스·장식이 핵심 흐름보다 앞서지 않는가?
3. **가독성**: 실제 렌더 폭에서 글자와 대비가 읽히는가? 작게 줄어드는 그림에는 원본 크기 보기 링크와 충분한 대체 텍스트를 제공한다.
4. **근거**: 그래프에는 출처·단위·측정 조건을 표시하고, 개념도와 가상 수치는 그 사실을 밝힌다. 효과나 안전을 보장하는 문구를 임의로 넣지 않는다.

검수에 실패하면 고쳐서 다시 확인한다. 품질을 확인하지 못한 그림을 완성된 결과라고 보고하지 않는다.

## 5. 본문 삽입과 자산 감사

- 마크다운 본문에 폭 전체 이미지로 넣고, 바로 앞뒤에서 노드와 흐름을 2~3문장으로 설명한다.

  ```markdown
  ![설명적인 alt 텍스트](/assets/images/<category>/<slug>.webp)

  [그림 크게 보기](/assets/images/<category>/<slug>.webp)
  ```

- 공식 원본에는 저작자·원문·적용 라이선스와 변환 사실을 캡션으로 남긴다. 직접 그린 도식은 원본과 출처를 혼동하지 않도록 구분한다.
- 작업 후 이미지의 실존, WebP 여부, 해상도(≤ 1400px), 용량(≤ 150KB)과 alt 텍스트를 확인한다.

```bash
python3 .agents/skills/tech-blog-diagrammer/scripts/make_diagram.py audit _posts/<category>/<post>.md --strict
```
