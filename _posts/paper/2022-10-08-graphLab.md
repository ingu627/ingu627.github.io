"Distributed GraphLab: A Framework for Machine Learning and Data Mining in the Cloud" 논문을 개인 공부 및 리뷰를 위해 정리한 글이다.

대규모 머신러닝 및 데이터 마이닝(MLDM) 알고리즘은 복잡한 데이터 의존성, 비대칭적인 수렴 속도, 비동기 파라미터 업데이트라는 고유한 특성을 갖는다. 기존의 MapReduce나 BSP 기반 Pregel은 이러한 비동기적이고 동적인 그래프 연산을 유연하게 처리하기에 구조적 한계가 존재했다. 저자들은 정점 중심(vertex-centric)의 순차 공유 메모리 추상화를 분산 환경으로 확장하여, 비동기 연산과 엄격한 직렬성(Serializability) 보장을 동시에 달성하는 분산 그래프 처리 프레임워크 Distributed GraphLab을 제안한다.

논문 출처 pdf : [GraphLab paper](https://arxiv.org/abs/1204.6078)

## 1. Introduction

머신러닝 및 데이터 마이닝(MLDM, Machine Learning and Data Mining) 문제의 데이터 규모가 폭발적으로 증가하면서, 대규모 클러스터 환경에서 MLDM 알고리즘을 효율적으로 병렬 분산 실행할 수 있는 특화 프레임워크의 필요성이 절실해졌다.

분산 MLDM 알고리즘을 직접 설계하고 구현하는 작업은 극심한 엔지니어링 병목을 초래한다. 개발자가 복잡한 수학적 수렴 모델을 구현하는 동시에 경쟁 상태(race condition), 데드락(deadlock), 분산 상태 동기화 및 통신 프로토콜까지 밑바닥부터 제어해야 하기 때문이다. 따라서 분산 시스템의 저수준 복잡성을 추상화 뒤로 숨기면서, MLDM 애플리케이션 특유의 비동기(asynchronous), 동적(dynamic), 그래프 병렬 연산을 자연스럽게 지원하는 상위 분산 추상화(abstraction)가 필수적이다.

- **추상화(abstraction)** : 복잡한 자료, 모듈, 시스템 등으로부터 핵심적인 개념 또는 기능을 간추려 내는 것을 말한다. [^3]

GraphLab 추상화는 공유 메모리 환경에서 검증된 정점 중심 연산 모델을 클라우드 및 분산 클러스터 환경으로 온전히 확장하고자 설계되었다.

분산 시스템의 동시성 복잡성을 덜어내고 알고리즘 본질에 집중하게 돕는 것이 GraphLab의 핵심 목표다.

## 2. MLDM Algorithm properties

MLDM 알고리즘은 일반적인 대규모 데이터 처리 작업과 뚜렷하게 구별되는 구조적·수학적 특성을 지니고 있으며, 이는 프레임워크 설계에 직접적인 요구사항으로 작용한다.

`Table 1`은 기존 대규모 병렬 프레임워크와 GraphLab의 특성을 비교 요약한 표이다.

![image](https://user-images.githubusercontent.com/78655692/194214665-e162a1d9-13a8-4c7b-ade2-9c9a8bed4bdf.png)
### Graph Structured Computation

최근 MLDM 분야의 발전은 데이터 간의 **의존성(dependency)**을 정교하게 모델링하는 데 초점을 맞추고 있다. 데이터 간의 상호 의존성을 구조화함으로써 노이즈가 심한 관측치로부터 더 신뢰도 높은 시그널을 추출할 수 있기 때문이다.

- **시그널(signal)** : 프로세스끼리 서로 통신할 때 사용하는 신호 체계다. [^1]
- **MapReduce의 한계**: 반복적인 상태 유지와 희소한 데이터 의존성 전파에 최적화되어 있지 않아 MLDM 그래프 계산에 비효율적이다.
- **버텍스 중심 모델의 등장**: 계산 의존성을 자연스러운 그래프로 표현하는 **Pregel** 및 **GraphLab**과 같은 그래프 병렬 추상화가 대안으로 부상했다.
- **버텍스(vertex)** : 그래프의 정점 혹은 노드(node)를 의미한다. [^2]
- **Pregel vs GraphLab 통신 모델**: 프리겔(Pregel)은 버텍스가 메시지를 주고받는 벌크 동기식(Bulk Synchronous Parallel, BSP) 모델인 반면, **GraphLab**은 각 버텍스가 인접한 버텍스와 에지(edge)의 데이터를 직접 읽고 쓸 수 있는 순차적(sequential) 공유 메모리 추상화를 채택한다.

GraphLab은 데이터의 물리적 이동(메시징) 대신 순차적 연산 논리에 집중할 수 있는 프로그래밍 환경을 제공한다.
### Asynchronous Iterative Computation

대다수 핵심 MLDM 알고리즘은 거대한 파라미터 세트를 반복적으로 갱신하며 수렴을 유도한다. 그래프 인접 구조(adjacency)에 따라 파라미터 업데이트는 이웃한 다른 파라미터 상태에 긴밀하게 의존한다.

- **동기(synchronous) 시스템**: 이전 타임스텝의 파라미터 값을 바탕으로 모든 파라미터를 동시에 갱신하므로, 가장 느린 노드(straggler)에 의해 전체 단계의 실행 시간이 결정되는 동기화 병목이 발생한다.
- **비동기(asynchronous) 시스템**: 다른 정점이 방금 갱신한 가장 최신의 파라미터 값을 즉각 반영하여 계산하므로 수렴 속도가 현저히 빨라진다.
- **동기 병목 유발 요인**: 워커 간 부하 불균형, 네트워크 지연, 하드웨어 성능 편차, 멀티 테넌시(Multi-Tenancy) 환경의 자원 간섭 등이 복합적으로 작용하여 동기식 시스템의 성능을 크게 저하시킨다.
  - **멀티 테넌시(Multi-Tenancy)** : 단일 소프트웨어 인스턴스 또는 인프라가 여러 독립된 클라이언트를 동시에 서비스하는 아키텍처다. [^4]
- **수렴 불균형**: 정점별 연산 복잡도와 국소 수렴 속도(local convergence rate)가 상이하므로, 그래프를 균등하게 분할하더라도 실행 시간의 극심한 편차가 불가피하다.

최신 파라미터를 즉시 참조하는 비동기 연산은 스트래글러 지연을 상쇄하고 수렴을 극적으로 앞당긴다.
### Dynamic Computation

반복 연산 과정에서 모든 정점이 동일한 횟수로 업데이트될 필요는 없으며, 파라미터의 중요도와 수렴 상태에 따라 동적으로 연산 자원을 배분해야 한다.

![image](https://user-images.githubusercontent.com/78655692/194474564-14f32298-e8fb-4548-abb4-7fc4c59db47c.png)

실제 MLDM 알고리즘에서 반복 계산은 고도로 비대칭적인 수렴 양상을 보인다. Fig 1(b)에서 확인되듯 대다수 버텍스는 단 한 번의 업데이트만으로 수렴하는 반면, 전체의 약 3%에 해당하는 버텍스만이 10회 이상의 집중적인 업데이트를 요구한다.

- **우선순위(priority) 기반 스케줄링**: 오차가 크거나 수렴이 더딘 파라미터에 연산 우선순위를 부여하면 불필요한 연산을 줄여 전체 수렴 속도를 가속할 수 있다. [^5]
- **적응형 연산 자원 집중**: 초기 연산을 민감한 파라미터에 선별 집중함으로써 전체 수렴 비용을 최소화한다 (Fig 1(c)).
- **Pregel vs GraphLab의 동적 계산 지원**: Pregel은 정점이 특정 슈퍼스텝에서 스스로 연산을 건너뛰는(vote to halt) 제한적 방식을 취하지만, GraphLab은 우선순위 스케줄링과 함께 인접 정점의 상태 변화에 따라 동적으로 연산을 스케줄링하는 유연한 적응형(adaptive) pull 모델을 온전히 지원한다.

모든 정점을 균등하게 돌리기보다, 오차가 큰 정점에 연산력을 집중하는 것이 수렴의 지름길이다.
### Serializability

병렬 알고리즘의 복잡한 동시성 제어 속에서도 순차 실행과 동일한 수학적 정합성을 보장하는 **직렬성(serializability)**은 알고리즘의 정확성과 신속한 수렴을 보장하는 핵심 요건이다.

모든 병렬 실행 결과가 어떤 순차적 실행 결과와 정확히 일치함을 보장하면, 개발자는 경쟁 상태나 데이터 오염에 대한 불안 없이 알고리즘의 수렴성에만 몰입할 수 있다. 많은 최적화 알고리즘은 직렬성이 보장될 때 수학적으로 증명된 수렴 속도를 발휘하며, 일부 알고리즘은 정확한 수렴을 위해 엄격한 직렬성을 필수 조건으로 요구한다.

GraphLab은 응용 알고리즘의 특성에 맞추어 병렬성과 일관성 사이의 트레이드오프를 조율할 수 있도록 다단계 일관성 모델을 제공한다.
## 3. DIST. GraphLab Abstraction

Distributed GraphLab의 프로그래밍 모델은 복잡한 분산 메모리 통신을 데이터 그래프, 업데이트 함수, 동기화 연산이라는 세 가지 핵심 추상화로 단순화한다.

![image](https://user-images.githubusercontent.com/78655692/194691481-ef86577f-7ac2-4aa4-8057-50baa015d9bb.png)

- **데이터 그래프(data graph)**: 수정 가능한 프로그램 전체 상태를 유지하며, 정점과 에지에 임의의 사용자 정의 데이터를 저장하고 희소한(sparse) 계산 의존성을 표현한다.
- **업데이트 함수(update function)**: 핵심 연산 단위로서, 중심 정점과 인접 에지 및 정점을 아우르는 **범위(scope)** 내의 데이터를 갱신하고 후속 실행을 예약하는 무상태(stateless) 프로시저다.
- **동기화 동작(sync operation)**: 백그라운드에서 분산 데이터 그래프 전체에 걸쳐 전역 통계(global aggregate)를 비동기적으로 지속 집계한다.
### 예제 1
 
- **페이지랭크(PageRank)** 알고리즘은 재귀적으로(recursively) 웹페이지 $v$의 랭크를 정의한다.
  - $R(v)=\frac{\alpha}{b}+(1-\alpha)$ $\ \sum_{u\ links\ to\ v}w_{u,v}\times R(\mu)$

### 3.1 Data Graph

프로그램의 전체 실행 상태는 방향성 그래프(directed graph) 형태의 데이터 그래프 컨테이너에 보관된다.

![image](https://user-images.githubusercontent.com/78655692/194707644-94204332-475d-4ef8-94a6-0299db0a84ba.png)

데이터 그래프 $G=(V,E,D)$는 사용자 정의 데이터 $D$를 관리하는 핵심 컨테이너다. 여기서 데이터란 모델 파라미터, 알고리즘 내부 상태, 통계 값 등을 포괄한다.

- **정점 및 에지 데이터 할당**: 사용자는 그래프의 정점 $\{D_v:v\in V\}$과 에지 $\{D_{u\to v}:\{u,v\}\in E\}$에 임의의 데이터 구조를 자유롭게 바인딩할 수 있다.
- **가변 상태와 정적 토폴로지**: 데이터 그래프에 저장된 데이터 값은 연산 중 수시로 갱신 가능하지만(mutable), 그래프의 정점·에지 연결 구조 자체는 정적(static)으로 유지되어 분산 파티셔닝의 안정성을 보장한다.
### 예제 2

- 데이터 그래프는 웹 그래프로부터 직접 얻는데, 각 버텍스는 웹페이지이고, 각 에지는 링크에 해당된다.
- 버텍스 데이터 $D_v$는 $R(v)$에 저장하며 에지 데이터 $D_{u\to v}$는 링크의 방향성 가중치인 $w_{u,v}$에 저장한다.

### 3.2 Update Functions

알고리즘의 실제 계산 로직은 데이터 그래프의 국소 범위를 변환하는 업데이트 함수로 정의된다.

업데이트 함수는 중심 정점 $v$의 범위(scope) $S_v$ 내 데이터를 읽고 수정하며, 인접한 정점들의 향후 연산을 큐 $\Gamma$에 스케줄링하는 무상태(stateless) 함수다.

  - **Update** : $f(v,S_v)\to (S_v,\Gamma)$

- **데이터 그래프 반영**: 함수 실행이 완료되면 수정된 스코프 데이터 $S_v$가 분산 데이터 그래프에 다시 기록된다.
- **적응형 스케줄링**: 함수가 반환한 정점 집합 $u\in \Gamma$는 GraphLab 런타임의 실행 의미론에 따라 스케줄러에 등록되어 추후 $f(u,S_u)$로 실행된다.
- **직접적인 공유 메모리 접근성**: 사용자는 명시적 메시지 패싱 없이 인접 정점과 에지의 데이터를 직관적으로 읽고 쓸 수 있어 프로그래밍 모델이 획기적으로 단순화된다.
- **Pregel 푸시 모델과의 차이**: Pregel은 수신된 메시지에 의해서만 연산이 트리거되고 전달된 메시지 페이로드에만 접근할 수 있는 반면, GraphLab은 인접 정점이 별도 갱신을 예약하지 않았더라도 최신 값을 자유롭게 읽을 수 있는 **pull** 모델을 자연스럽게 구현한다.

### 예제 3

- 페이지랭크에 대한 업데이트 기능은 인접 버텍스의 현재 랭크의 가중치 합을 계산하고 이를 현재 버텍스의 랭크로 할당한다.
- 현재 버텍스의 값이 미리 정의된 임계값 이상으로 변경되는 경우에만 이웃이 업데이트되도록 예약한다.

### 3.3 The GraphLab Execution Model

GraphLab 런타임은 입력 그래프와 초기 정점 큐를 바탕으로 직렬성을 유지하며 병렬 연산을 구동한다.

![image](https://user-images.githubusercontent.com/78655692/194694343-a9232ad7-e418-424a-85b1-7acf259c5254.png)

GraphLab의 입력은 데이터 그래프 $G=(V,E,D)$, 업데이트 기능, 실행할 초기 정점 셋 $\Gamma$로 구성된다. 런타임 엔진은 작업 큐 $\Gamma$가 빌 때까지 정점을 반복 추출하여 병렬 실행하며, 완료 시 최종 데이터 그래프와 집계된 전역 값을 사용자에게 반환한다.

분산 환경에서 최대의 병렬 처리 효율을 끌어내기 위해, GraphLab은 단일 머신 공유 메모리 시절의 엄격한 순차 실행 순서 제약을 완화하고 런타임이 직렬성을 훼손하지 않는 한도 내에서 최적의 실행 순서를 자유롭게 선택하도록 허용한다.
### 3.4 Ensuring Serializability

병렬 실행 환경에서 직렬성을 보장하기 위해서는 동시에 실행되는 업데이트 함수들의 범위(scope) 충돌을 엄밀히 제어해야 한다.

GraphLab은 복수의 워커 스레드가 동일한 데이터 그래프에서 동시에 서로 다른 정점의 스코프를 실행할 수 있도록 지원하며, 이때 중첩된(overlapping) 스코프 간의 동시 쓰기 충돌을 차단함으로써 유효한 순차 실행 일정과 수학적으로 일치하는 직렬성(serializability)을 보장한다.

- **완전 일관성(full consistency)**: 동시에 실행되는 업데이트 함수의 스코프가 단 하나의 정점이나 에지도 겹치지 않도록 강제하는 방식이다. 충돌을 완벽히 차단하지만, 동시에 실행되는 정점 간에 최소 2홉(hop) 이상의 거리가 요구되므로 병렬성이 크게 제약된다 (Fig 2(c) 참조).

![image](https://user-images.githubusercontent.com/78655692/194696868-54237d55-a5a3-490f-8fdc-ee246660b7c7.png)

- **에지 일관성(edge consistency)**: 대부분의 머신러닝 알고리즘에서 업데이트 함수가 인접 정점의 데이터를 수정하기보다는 단순히 참조(read-only)만 한다는 점에 착안한 모델이다.
  - 중심 정점과 인접 에지에 대해서는 배타적 읽기/쓰기(read-write) 권한을 부여한다.
  - 인접 정점에 대해서는 읽기 전용(read-only) 권한만 허용한다 (Fig 2(b) 참조).
  - 스코프가 인접 정점을 매개로 일부 겹치더라도 안전하게 병렬 실행될 수 있어 클러스터 전반의 동시성을 대폭 극대화한다 (Fig 2(c) 참조).

에지 일관성은 엄격한 수학적 직렬성을 지키면서도 병렬 처리율을 끌어올리는 핵심 장치다.
### 3.5 Sync Operation and Global Values

분산 환경 전반에 걸쳐 모델의 수렴 판정이나 목적 함수 값을 계산하기 위해서는 전역 통계를 실시간으로 유지해야 한다.

GraphLab의 동기화 연산(sync operation)은 Pregel의 집계와 유사하게 결합법칙과 교환법칙이 성립하는 연산(associative commutative sum)을 통해 전역 상태를 계산한다.

  - $Z=Finalize(\bigoplus_{v\in V}Map(S_v))$

- **지속적인 백그라운드 집계**: 모든 계산을 일시 정지하고 슈퍼스텝 경계에서만 집계하는 Pregel과 달리, GraphLab의 동기화 연산은 전역 값의 업데이트된 추정치를 유지하기 위해 백그라운드에서 비동기적으로 지속 실행된다.
- **직렬성과의 트레이드오프**: 모든 업데이트 함수가 전역 값에 실시간으로 접근할 수 있으므로, 업데이트 함수와 관련하여 동기화 동작의 엄격한 직렬성을 보장하는 것은 모든 분산 연산을 동기화하고 중지해야 하므로 극히 비용이 많이 든다. 따라서 실용적인 분산 MLDM 환경에서는 전역 통계에 대해 약간 완화된 일관성을 허용하는 절충안을 채택한다.
## 4. Distributed GraphLab Design

분산 메모리 환경에서 대규모 그래프와 동적 비동기 연산을 안정적으로 구동하기 위한 물리 아키텍처와 파티셔닝 전략을 살펴본다.

분산 GraphLab 시스템의 전체 설계 개요는 아래 그림과 같다.

![image](https://user-images.githubusercontent.com/78655692/194700580-928569c6-ab6c-4e42-8664-a03f066376d9.png)

동적(dynamic) 비동기(asynchronous) 그래프 알고리즘에 공통적으로 나타나는 임의의 메모리 접근 패턴 때문에, GraphLab은 전체 그래프와 모든 프로그램 상태가 물리 RAM에 상주해야 하는 분산 인메모리(in-memory) 아키텍처에 중점을 둔다.

- **인메모리(in-memory) 컴퓨팅** : 메모리 내에서 데이터의 저장뿐 아니라 데이터의 연산까지 고속으로 수행하는 최첨단 기술이다. [^6]
- **아톰(atom) 기반 오버 파티셔닝**: 데이터 그래프는 도메인 특정 지식을 활용하거나 분산 그래프 분할 휴리스틱을 사용하여 실제 물리 머신 수보다 훨씬 많은 $k$개의 아톰(atom) 부분으로 과분할(over-partitioning)된다. 각 아톰은 HDFS나 Amazon S3와 같은 분산 스토리지 시스템에 별도의 파일로 저장된다.
- **바이너리 저널 구조**: 각 아톰 파일은 `AddVertex(5000, vdata)` 및 `AddEdge(42\to314, edata)`와 같은 명령을 생성하는 그래프의 간단한 바이너리 압축 저널이다.
- **고스트(ghosts) 캐시 계층**: 각 아톰은 파티션 경계에 인접한 외부 버텍스 및 에지 집합인 **고스트(ghosts)**에 대한 정보를 저장한다. 네트워크 전체에서 실제 정점에 대응하는 로컬 캐시 역할을 수행한다.
- **동적 로드 밸런싱과 고스트 재생**: $k$개 아톰의 연결 구조와 파일 위치는 아톰 인덱스 파일에 $k$ 버텍스와 아톰 연결을 인코딩하는 에지가 있는 메타 그래프로 저장된다. 물리적 머신 수에 맞춰 메타 그래프의 빠른 로드 밸런싱을 수행한 뒤, 각 머신은 할당된 아톰의 저널을 재생(playback)하여 그래프의 로컬 파티션과 고스트를 메모리에 인스턴스화한다.
- **캐시 일관성(cache consistency)**: 에지 가중치처럼 변경되지 않는 불변 데이터의 전송을 제거하는 간단한 버전 관리 시스템을 사용하여 캐시 일관성을 효율적으로 관리한다.
### 4.2 Distributed GraphLab Engines

분산 GraphLab 엔진은 3.3 섹션에 정의된 실행 모델을 에뮬레이트(emulate)하고 업데이트 기능 및 동기화 작업을 실행하며, 예정된 버텍스 셋 $\Gamma$를 유지하고 적절한 일관성 모델과 관련하여 직렬성을 보장한다.

### 4.2.1 Chromatic Engine

정점 채색(graph coloring) 기법을 활용하면 복잡한 락 없이도 결정론적인 직렬성을 간단하게 확보할 수 있다.

인접한 버텍스가 같은 색(color)을 공유하지 않도록 각 버텍스에 색을 할당하는 고전적 기법을 분산 환경에 적용한다.

- **색상 단계(color-step)**: 데이터 그래프의 버텍스 색상이 주어지면 다음 색상으로 진행하기 전에 버텍스 셋 $\Gamma$에서 동일한 색상의 모든 버텍스를 동기적으로 실행하여 에지 일관성 모델을 만족시킬 수 있다. BSP 모델의 슈퍼스텝과 유사하게 단일 색상 내의 모든 버텍스를 업데이트하고 변경 사항을 전달하는 프로세스를 색상 단계라고 부른다.
- **안전한 동기화 지점**: 색상 단계와 색상 단계 사이의 경계에서 전역 동기화 작업을 안전하게 실행할 수 있다.
- **비동기 고스트 전파**: 크로매틱 엔진이 동기식 색상 단계로 작동하는 동안 고스트 버텍스 및 에지에 대한 변경 사항은 변경 즉시 비동기식으로 네트워크에 전달된다. 결과적으로 크로매틱 엔진은 각 색상 단계 내에서 네트워크 대역폭과 프로세서 시간을 효율적으로 사용한다.
### 4.2.2 Distributed Locking Engine

완전 비동기 실행 환경에서 임의의 일관성 모델을 지원하기 위해 GraphLab은 분산 Reader-Writer 락 메커니즘을 사용한다.

![image](https://user-images.githubusercontent.com/78655692/194706381-0583ef5e-915c-48c5-8f23-922205179df8.png)

GraphLab은 각 버텍스에 Reader-Writer 락(lock)을 연결하여 분산된 상호 배제(mutual exclusion)를 달성하며, 서로 다른 락 프로토콜을 적용하여 일관성 모델을 유연하게 구현한다.

- **버텍스 일관성(vertex consistency)**: 요청된 각 범위의 중앙 버텍스에 대한 쓰기 락을 획득하여 달성된다.
- **에지 일관성(edge consistency)**: 중앙 버텍스에 대한 쓰기 락을 획득하고 인접 버텍스에 대한 읽기 락을 획득하여 달성된다.
- **완전 일관성(full consistency)**: 중앙 버텍스와 모든 인접 버텍스에 대한 배타적 쓰기 락을 획득하여 달성된다.
- **데드락 방지 순서화**: 데드락은 머신 ID 다음에 버텍스 ID가 오는 사전식 순서 `(owner(v), v)`에 따라 순차적으로 락을 획득하여 방지한다.
- **로컬 연산 원칙**: 그래프가 파티셔닝되어 있으므로 각 머신은 로컬 버텍스에서만 업데이트를 실행하며, 고스트 버텍스/에지를 통해 원격 범위의 모든 정보에 직접 메모리로 접근한다.

![image](https://user-images.githubusercontent.com/78655692/194705203-1b601118-c18b-4e81-bef0-0290c171a713.png)

각 머신의 워커(worker) 스레드는 스케줄러가 비어 있을 때까지 위 알고리즘 루프를 실행하며 분산 연산을 지속한다.
### Pipelined Locking and Prefetching

분산 락 획득 과정에서 발생하는 원격 네트워크 왕복 지연을 은폐하기 위해 파이프라인과 프리페치 기법을 도입했다.

각 머신은 락이 요청되었지만 아직 충족되지 않은 버텍스 파이프라인을 유지 관리하며, 락 획득 및 데이터 동기화를 완료한 버텍스는 파이프라인을 떠나 워커 스레드에 의해 즉시 실행된다.

![image](https://user-images.githubusercontent.com/78655692/194706094-758e91d9-a626-41fa-9edd-278a5a3b28d7.png)

- **논블로킹 콜백 락**: 일반 Reader-Writer 락은 경합 시 파이프라인 스레드를 블로킹하기 때문에 사용할 수 없으므로, 완료 시 콜백을 호출하는 non-blocking 변형 Reader-Writer 락을 구현했다.
- **분산 연속 전달(Distributed Continuation Passing)**: 락 요청은 머신 간에 순서대로 전달되는 콜백 체인을 통해 분산 환경에서 비동기적으로 연쇄 처리된다.
- **조기 데이터 동기화**: 지연 시간(latency)을 줄이기 위해 각 머신이 로컬 락을 완료하는 즉시 원격 락 데이터의 동기화가 병행 수행된다.

![image](https://user-images.githubusercontent.com/78655692/194706329-06a95753-aa1e-478d-80c9-b2dd0f225c73.png)

락 획득과 원격 데이터 프리페치를 파이프라인화함으로써 네트워크 지연을 연산 시간 뒤로 완전히 숨긴다.
### 4.3 Fault Tolerance

대규모 분산 클러스터에서 노드 장애에 대응하기 위해 분산 **체크포인트(checkpoint)** 메커니즘을 사용하여 분산 GraphLab 프레임워크에 장애 허용(fault tolerance)을 도입한다.

장애가 발생한 경우 시스템은 마지막 체크포인트에서 안정적으로 복구된다. GraphLab은 분산 **스냅샷(snapshot)** 생성을 위해 두 가지 전략을 평가한다.

- **동기식 스냅샷**: 업데이트 기능의 실행을 일시 중단하고 모든 통신 채널을 플러시(flush)한 다음, 마지막 스냅샷 이후 수정된 모든 데이터를 분산 파일 시스템의 저널 파일에 저장하는 방식이다.
- **비동기식 Chandy-Lamport 스냅샷**: 계산을 중단하지 않고 스냅샷을 점진적으로 생성하는 방식이며, GraphLab은 **Chandy-Lamport 스냅샷**을 기반으로 완전 비동기식 대안을 설계했다.

![image](https://user-images.githubusercontent.com/78655692/194706737-d1b0e389-54e5-44f9-94f0-9fcf67d85d6b.png)

Alg 5는 업데이트 기능으로 표현되며 다음 조건에서 일관된 스냅샷을 보장한다:
1. 에지 일관성은 모든 업데이트 기능에 사용된다.
2. 스케줄은 범위가 락이 해제되기 전에 완료된다.
3. 스냅샷 업데이트는 다른 업데이트 기능보다 우선시된다.

동기 및 비동기 스냅샷은 모두 고정된 간격으로 시작되며, 간격 선택은 장애 시 손실된 계산과 체크포인트 구성 비용의 균형을 맞춰 결정된다:

  - $T_{interval}=\sqrt{2T_{checkpoint}T_{MTBF}}$

### 4.4 System Design

GraphLab은 마스터 노드의 병목 없이 모든 워커가 대칭적으로 동작하는 완전 분산 대칭 아키텍처를 구현했다.

![image](https://user-images.githubusercontent.com/78655692/194707034-ae7c613b-0746-4ad2-9b10-191c460ce9c1.png)

Fig 5(a)는 GraphLab 시스템의 개요를, Fig 5(b)는 GraphLab 락 엔진 구현의 개요를 보여준다. GraphLab이 클러스터에서 실행되면 각 머신에서 프로그램 인스턴스가 대칭적(symmetric)으로 구동되며, TCP/IP 비동기 RPC를 통해 마스터 없이 직접 통신한다.

- **프로세스 및 파티션 관리**: 각 **프로세스**는 로컬 그래프 스토리지 내에서 관리되는 분산 그래프의 파티션을 담당하고 분산 락을 호스팅한다.
- **캐시(Cache)**: 원격 그래프 데이터에 대한 효율적인 인메모리 액세스를 제공한다.
- **스케줄러와 프리페치 파이프라인**: 각 프로세스는 할당된 $\Gamma$의 버텍스를 관리하는 **스케줄러**를 포함한다. 런타임에 로컬 스케줄러는 실행에 필요한 데이터와 락을 수집하는 prefetch 파이프라인에 버텍스를 공급하며, 모든 조건이 충족되면 워커 스레드 풀에 의해 병렬 실행된다.
- **분산 스케줄링**: 버텍스 스케줄링은 로컬 버텍스에 대한 스케줄을 관리하고 원격 버텍스에 대한 요청을 전달하는 각 머신으로 분산된다.
- **분산 합의(Distributed Consensus)**: 모든 스케줄러가 비어 있는 종료 시점을 감지하기 위해 **분산 합의 알고리즘**을 사용한다.

중앙 집중식 병목 현상이 없는 완전 대칭 설계 덕분에 클러스터 규모에 비례하는 선형적 확장이 가능하다.

## 핵심 요약 및 시사점

- **비동기 정점 중심 추상화**: Pregel의 벌크 동기식(BSP) 메시징 한계를 넘어, 공유 메모리 스타일의 스코프(Scope) 접근을 통해 최신 파라미터를 즉시 참조하는 비동기 연산과 적응형 동적 스케줄링을 성공적으로 지원했다.
- **에지 일관성을 통한 병렬성 극대화**: 엄격한 직렬성(Serializability)을 유지하면서도, 인접 정점에 대해 읽기 전용 권한을 부여하는 에지 일관성 모델을 도입하여 동시성 처리율을 대폭 확장했다.
- **분산 락과 파이프라인 프리페치**: 사전식 순서 기반 Reader-Writer 락과 비동기 콜백 체인(Pipelined Locking)을 결합하여, 분산 환경의 원격 통신 레이턴시를 연산 뒤로 효과적으로 은폐했다.
- **무중단 Chandy-Lamport 스냅샷**: 비동기 연산의 흐름을 멈추지 않고도 수학적으로 정합한 체크포인트를 생성할 수 있는 알고리즘을 구축하여 안정적인 장애 허용(Fault Tolerance)을 달성했다.

GraphLab은 복잡한 데이터 의존성과 비대칭 수렴을 갖는 대규모 MLDM 알고리즘에 있어, 비동기 분산 그래프 처리가 왜 필수적인지 그 설계 원칙과 기법을 정립한 기념비적 프레임워크다.
