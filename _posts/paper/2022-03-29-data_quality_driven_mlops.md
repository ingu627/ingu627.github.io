"A Data Quality-Driven View of MLOps" 논문을 공부하며 핵심 내용을 정리하고 리뷰한 글이다.

머신러닝 시스템의 성능 저하는 모델 아키텍처 결함보다 데이터 파이프라인의 불완전성에서 기인하는 경우가 훨씬 많다. 본 논문은 MLOps의 4대 핵심 과제(품질 최적화, 타당성 검증, 과적합 방지 테스트, 연속 품질 평가)를 데이터 품질의 전파 및 관리 관점에서 재정의하고 실질적인 해결 방향을 제시한다.

논문 원문 링크: <https://arxiv.org/abs/2102.07750>

## 1. Introduction

머신러닝 모델은 코드 작성만으로 완성되는 일반 소프트웨어와 달리, 대규모 데이터셋을 컴파일하여 생성하는 소프트웨어 아티팩트(software artifact)에 가깝다. 따라서 모델의 안정적인 서빙과 성능 유지를 위해서는 전통적인 DevOps를 넘어선 MLOps 파이프라인이 필수적이다.

전통적인 DevOps가 빠른 개발 주기와 무중단 배포를 목표로 한다면, MLOps는 데이터 품질의 변화가 모델 예측력에 미치는 영향까지 제어해야 한다. 모델의 정확성(accuracy), 공정성(fairness), 견고성(robustness)은 훈련 데이터에 내재된 노이즈, 불균형, 적대적 섭동과 직결되기 때문이다. 결국 MLOps를 체계적으로 이해하고 최적화하기 위한 핵심 열쇠는 바로 **데이터 품질(data quality)**에 있다.

- **DevOps의 정의**: 시스템 개발 라이프사이클을 단축하고 고품질 소프트웨어를 지속적으로 제공(CI/CD)하는 프로세스.
- **모델 품질과 데이터 품질의 상관관계**: 모델의 정확도와 강건성은 기초 데이터의 노이즈, 레이블 불균형, 결측치 수준에 직접적으로 종속된다.
- **데이터 중심 품질 개선**: 새로운 모델 아키텍처 탐색 못지않게 데이터 정제(cleaning), 통합(integration), 레이블 확보(label acquisition)가 모델 성능 향상의 핵심 동력으로 작용한다.

지금까지 학계와 산업계에서는 데이터 품질의 특정 측면을 개선하기 위해 다양한 시스템을 제안해 왔다.

- **data acquisition with weak supervision (Snorkel)**: 약지도 학습을 통한 레이블 자동 생성 및 확장
- **ML engineering pipelines (TFX)**: 프로덕션 레벨 ML 파이프라인 표준화 및 유효성 검증
- **data cleaning (ActiveClean)**: 모델 예측 손실을 기반으로 한 반복적·능동적 데이터 정제
- **data quality verification (Deequ)**: 대규모 데이터셋에 대한 단위 테스트 및 제약 조건 자동 검증
- **interaction (Northstar)**: 인터랙티브 데이터 과학 및 직관적 시각화 도구
- **fine-grained monitoring and improvement (Overton)**: 모델 라이프사이클 전반에 걸친 세부 모니터링 및 자동 튜닝

### Data Quality에 대한 4가지 측면

데이터 품질은 단일 지표로 규정되지 않으며, 문제 해결 맥락에 따라 다음 4가지 핵심 축으로 분류된다.

|속성|설명|
|---|---|
|정확성(accuracy)|데이터가 정확하고 신뢰할 수 있으며, 작업에 대해 인증된 정도|
|완전성(completeness)|특정 데이터 수집에 대응(corresponding)하는 데이터를 포함하는 정도|
|일관성(consistency)|데이터 집합에서 정의된 의미 규칙 위반의 정도|
|적시성(timeliness)|작업을 위한 데이터가 최신인 정도|

결국 데이터 파이프라인의 품질이 곧 프로덕션 모델의 예측 한계를 규정한다.

## 2. Machine Learning Preliminaries

머신러닝 모델의 배포 이후 성능 저하는 대부분 데이터 생성 분포의 동적 변화에서 비롯된다.

기본적인 머신러닝 선수 지식 중에서도 MLOps 관점에서 가장 치명적인 통계적 분포 변화 개념들을 정리한다.

### Concept Shift

입력과 라벨의 결합 확률 분포 $P(X,Y)$가 시간에 따라 고정되어 있다는 정적 가정은 실제 프로덕션 환경에서 쉽게 깨진다. 이러한 시간 경과에 따른 확률 분포 변화를 **concept shift**라고 통칭한다.

특징 공간 $X$와 라벨 공간 $Y$의 정의 자체가 바뀌는 현상은 **data drift**라 부르며, 이로 인해 서빙 시 결측치나 이상치가 급증할 수 있다. 한편 분포 변화의 세부 양상은 사후 확률의 변동 여부에 따라 다음과 같이 나뉜다.

- **real drift (model drift)**: 입력 분포 $p(X)$의 변화가 사후 확률 $p(Y\mid X)$의 변화를 유발하는 경우. 실제 결정 경계가 이동하므로 모델 성능이 직접적으로 하락한다.
- **virtual drift**: 입력 분포 $p(X)$는 변하지만 사후 확률 $p(Y\mid X)$는 그대로 유지되는 경우.
  - $X$ feature 전반에 걸쳐 posterior probability distribution이 안정적으로 유지된다면, virtual drift 자체는 모델의 결정 경계에 영향을 주지 않는다.

데이터 분포는 정적이지 않으며, 프로덕션 환경에서는 drift의 유형을 판별하는 것이 급선무다.

![image](https://user-images.githubusercontent.com/78655692/161371447-7a288d5a-4527-4b50-a759-d03ae087d281.png)
### 추가 : 어떻게 방지해야 하나? [^1]

분포 변화에 실시간으로 대응하기 위해 실무에서는 다양한 완화 전략을 채택한다.

1. **Online learning**: 모델이 한 번에 하나의 스트리밍 샘플을 처리함에 따라 가중치를 즉시 업데이트
2. **Periodically re-train the model**: 성능 저하나 윈도우 간 drift 감지 등 특정 트리거 발생 시 모델 재학습
   - 모델 성능이 지정된 임계값 미만으로 저하되거나, 두 개의 슬라이딩 윈도우 사이에서 유의미한 drift가 관찰될 때 실행
3. **Periodically re-train on a representative subsample**: drift 발생 시 전체 모집단을 대표하고 최신 분포를 반영하는 서브샘플을 선별하여 재학습
4. **Ensemble learning with model weighting**: 여러 시점의 모델을 앙상블하고 최근 데이터에 대한 성능을 바탕으로 가중 평균을 적용
5. **Feature dropping**: 개별 피처의 기여도를 모니터링하여 drift로 인해 AUC-ROC 등 성능 지표를 훼손하는 피처를 선제적으로 폐기

이처럼 지속적인 완화 전략을 갖추는 것과 동시에, MLOps 파이프라인 각 태스크에서 발생하는 구체적인 데이터 품질 과제를 해결해야 한다.

## 3. MLOps Task 1: Effective ML Quality Optimization

모델 품질 향상의 출발점은 결함 있는 학습 데이터를 선별하고 효과적으로 정제하는 최적화 작업이다.

MLOps의 핵심 과제 중 하나는 훈련 데이터의 결함을 개선하여 모델 품질을 극대화하는 것이다. 아키텍처 튜닝 외에도 노이즈와 결측치를 정제하는 데이터 클리닝(data cleaning)이 필수적이다.

### MLOps Challenge

데이터셋 내 모든 노이즈와 오염(dirty) 샘플이 최종 모델 성능에 동일한 비중으로 악영향을 미치는 것은 아니다.

무작정 모든 결측과 오염을 전수 정제하려는 시도는 비용 대비 효과가 떨어지는 하위 최적(sub-optimal) 접근이다. 실무 데이터 정제는 대부분 인간 작업자의 개입을 동반하는 반자동(semi-automated) 방식으로 진행되므로, 모델 성능 개선에 결정적인 영향을 미치는 샘플을 우선 선별하여 사람의 개입 비용을 최소화하는 전략이 요구된다.

### A Data Quality View

불완전하고 노이즈가 많은 학습 데이터가 모델 학습 과정에서 어떻게 전파되는지 그 인과관계를 수학적으로 모델링해야 한다.

- **ActiveClean**: 손실 함수 기울기를 기반으로 모델 정확도 향상에 가장 기여도가 높은 샘플을 점진적으로 선별·정제
- **CPClean**: 순차적 정보 최대화(sequential information maximization)를 바탕으로 데이터 노이즈 전파 과정(noise propagation process)을 체계적으로 분석하여 최적의 정제 우선순위를 산출

무차별 정제 대신 모델 영향도에 따른 선택적 정제가 효율성의 핵심이다.

## 4. MLOps Task 2: Preventing Unrealistic Expectations

본격적인 모델 개발에 앞서 달성 가능한 이론적 성능 한계를 사전 추정하여 불필요한 리소스 낭비를 막아야 한다.

전통 소프트웨어 공학에서는 프로젝트 착수 전 타당성 조사(feasibility study)를 거쳐 실패 위험을 사전에 방지한다. 반면 머신러닝 개발 환경에서는 데이터셋의 본질적 한계를 미리 측정하지 못한 채 무리한 개발에 착수하여 시간과 비용을 낭비하는 경우가 흔하다.

### MLOps Challenge

주어진 데이터셋에서 고비용의 모델 학습을 전부 거치지 않고도 이론적인 최소 오류율을 사전에 추정할 수 있어야 한다.

이는 축소 불가능한 오류(irreducible error)로 불리는 베이즈 오류율(Bayes Error Rate, BER)의 추정 문제로 귀결된다. 그러나 실무에서 작동 가능한 신뢰도 높은 BER 추정기(estimator)를 구축하는 것은 여전히 까다로운 연구 과제다.

1. **수십 년간 축적된 BER 추정 이론을 실무 파이프라인에 접목하는 방법**
2. **계산 복잡도와 추정 정확도 사이의 최적 트레이드오프 도출**

### Non-Zero Bayes Error and Data Quality Issues

BER이 0이 되지 않는 근본 원인은 데이터 품질의 결함, 특히 완전성과 정확성의 결여에서 비롯된다.

- **완전성(completeness) 결여**: 피처 공간이나 라벨 공간의 정의가 불충분하여 클래스 구분에 필요한 핵심 정보가 누락된 경우
- **정확성(accuracy) 결여**: 라벨링 오류나 센서 노이즈로 인해 입력 대비 레이블의 신뢰도가 떨어지는 경우

수학적 관점에서 0이 아닌 BER은 동일하거나 유사한 입력 피처에 대해 서로 다른 클래스 확률이 겹치는 **중복 사후 확률(overlapping posterior probabilities)** 현상에서 기인한다. 즉, 특정 입력에 대해 유일하고 완벽한 라벨이 존재하지 않는 상태다.

![image](https://user-images.githubusercontent.com/78655692/160673572-e2711f74-e41b-47b9-99d5-f100fe8e4fc3.png)

### A Data Quality View

실용적인 BER 추정기를 파이프라인에 내재화하기 위해서는 다음 두 가지 공학적 제약을 극복해야 한다.

1. **연산 요구량(computational requirements)**: 신뢰할 수 있는 통계적 추정치를 도출하기 위해 방대한 데이터가 요구되며, 이에 따른 계산 비용이 급증한다.
2. **하이퍼파라미터 민감도(hyperparameter selection)**: 타당성 검증 단계에서는 데이터의 사전 분포 정보가 제한적이므로, 추정 알고리즘이 하이퍼파라미터 변동에 둔감(robust)해야 한다.

이론적 오류 한계를 먼저 파악해야 비현실적인 목표 설정을 피할 수 있다.


## 5. MLOps Task 3: Rigorous Model Testing Against Overfitting

테스트 데이터셋의 반복적 재사용으로 인해 발생하는 과적합(adaptive overfitting)을 엄밀히 제어해야 한다.

소프트웨어 공학의 지속적 통합(Continuous Integration, CI)은 빌드 및 테스트를 자동화하여 회귀 버그를 방지한다. 그러나 머신러닝 환경에서 동일한 테스트셋을 CI 파이프라인에서 무분별하게 재사용하면, 개발자가 테스트셋의 피드백에 맞춰 모델을 암묵적으로 과적합시키는 심각한 위험이 발생한다.

### MLOps Challenge

이상적인 평가를 위해서는 테스트셋을 단 한 번만 평가에 사용하거나, 개발자로부터 평가 데이터를 완전히 은닉(obfuscated)해야 한다.

그러나 지속적인 모델 개선과 잦은 배포가 일어나는 현실적인 엔지니어링 환경에서 테스트셋을 매번 폐기하거나 완전히 격리하는 것은 불가능에 가깝다.

### A Data Quality View

프로덕션 레벨에서 신뢰성 있는 지속적 모델 테스트를 구축하기 위해서는 두 가지 통계적 난제를 해결해야 한다.

1. **테스트 결과의 확률적 무작위성**: ML 태스크와 모델의 특성상 단일 테스트 결과는 확률적 노이즈를 포함한다. 이는 통계 이론의 집중 부등식(concentration bound)을 활용해 허용 오차 한계를 수학적으로 제한함으로써 완화한다.
2. **테스트셋 재사용에 따른 적응적 과적합(adaptive overfitting)**: 개발자가 피드백을 수신하며 동일한 테스트셋을 반복 평가할 경우 일반화 신뢰도가 급감한다. 한정된 데이터셋의 일반화 보장을 유지하면서 안전하게 재사용할 수 있는 유효 테스트 횟수를 통계적으로 통제해야 한다.

### Limitations

현재 테스트 체계에도 여전히 근본적인 한계점이 존재한다.

- **숨겨진 테스트셋에 대한 의도적 과적합**: 개발자가 은닉된 검증셋의 패턴을 간접 피드백을 통해 역추적하여 과적합을 시도할 경우 이를 완벽히 방어하기 어렵다.
- **concept shift 대응력 부재**: 고정된 테스트셋 중심의 평가는 시간 경과에 따라 발생하는 실제 운영 환경의 동적 분포 변화를 포착하지 못한다.

테스트 데이터셋의 재사용 횟수를 수학적으로 통제하지 못하면 CI 검증은 무의미해진다.
## 6. MLOps Task 4: Efficient Continuous Quality Testing

동적으로 유입되는 무라벨 서빙 데이터 스트림 속에서 최적의 모델을 최소한의 라벨링 비용으로 연속 선별해야 한다.

DevOps의 핵심은 시스템 변경에 신속하게 적응하며 견고성을 유지하는 데 있다. 반면 프로덕션 MLOps에서는 서빙 데이터의 분포가 예고 없이 변화(distribution shift)하여 기학습된 모델의 실전 성능이 급격히 저하되는 현상이 빈번하다.

### MLOps Challenge

라벨이 주어지지 않은 대규모 프로덕션 데이터 스트림 환경에서 현재 시점에 가장 우수한 모델을 정확히 선택하는 것이 핵심 과제다.

모든 스트리밍 데이터에 인간 작업자가 라벨을 부착하는 것은 천문학적인 비용을 초래하므로, MLOps 관점에서는 모델 간 우열을 가리는 데 필요한 최소한의 라벨링만 선별 수행해야 한다.

### A Data Quality View

Concept shift는 데이터 품질의 4대 축 중 **적시성(timeliness)**과 밀접하게 연동된다.

운영 환경에 사전 배포된 여러 후보 모델들은 시간에 따른 데이터 분포 변화를 서로 다른 방식으로 반영하고 있다. 따라서 전체 스트림을 라벨링하는 대신, 모델 간 예측 불일치가 크거나 신뢰도가 떨어지는 핵심 샘플에만 라벨링 리소스를 집중해야 한다. 이를 통해 제한된 라벨링 비용으로도 최적의 모델을 신속하게 식별하고, 불완전한 평가 데이터에 대한 과도한 의존을 탈피할 수 있다.

결국 운영 환경의 MLOps는 최소 비용의 적응형 라벨링으로 적시성을 방어하는 싸움이다.

## 핵심 요약 및 시사점

본 논문은 MLOps를 단순한 파이프라인 자동화 툴체인이 아닌, **데이터 품질의 전파 및 제어 프로세스**라는 통일된 시각으로 재구성했다.

- **데이터 중심 품질 최적화**: 무차별적 전수 정제 대신, 모델 예측 손실에 실질적인 영향을 주는 샘플을 선별 정제하여 인간 개입 비용을 최소화해야 한다.
- **타당성 검증(BER 사전 추정)**: 모델 개발에 돌입하기 전 베이즈 오류율을 추정함으로써 데이터 피처와 라벨의 고유 한계를 진단하고 비현실적인 기대를 방지해야 한다.
- **적응적 과적합 방지 CI**: 지속적 통합 파이프라인에서 테스트 데이터 재사용 한계를 통계적 집중 부등식으로 제어하여 검증 신뢰성을 확보해야 한다.
- **적시성 기반 연속 품질 평가**: 서빙 스트림에서 발생하는 concept shift에 대응하기 위해, 능동적 샘플링과 최소한의 라벨링으로 최적 모델을 신속히 선별해야 한다.

결론적으로 견고한 MLOps 플랫폼 구축을 위해서는 알고리즘 개발보다 데이터 품질의 4대 속성(정확성, 완전성, 일관성, 적시성)을 파이프라인 전 단계에서 정량적으로 관리하는 체계가 선행되어야 한다.
