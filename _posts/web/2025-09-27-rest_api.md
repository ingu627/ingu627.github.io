현대 소프트웨어 개발에서 "REST API를 구축한다"는 표현은 흔히 단순히 HTTP 위에서 JSON 데이터를 주고받는 엔드포인트를 만든다는 의미로 오용되곤 한다. 그러나 2000년 로이 필딩(Roy Fielding)이 박사 학위 논문에서 정립한 **REST(Representational State Transfer)**는 단순한 데이터 교환 포맷이 아니라, 웹(Web)의 경이로운 확장성(Scalability)과 수십 년간의 불변성을 유지할 수 있도록 고안된 엄격한 **분산 하이퍼미디어 아키텍처 스타일**이다.

잘못 설계된 API는 리소스 간 결합도를 높이고, 클라이언트와 서버의 독립적인 배포를 저해하며, 캐싱과 로드밸런싱 인프라의 혜택을 무력화한다. 이 글에서는 로이 필딩의 6대 아키텍처 제약조건과 리차드슨 성숙도 모델(Richardson Maturity Model), RFC 9110 HTTP 시맨틱스의 멱등성(Idempotency) 원리, 그리고 파이썬 FastAPI 프레임워크를 활용해 고성능 프로덕션 API를 구현하는 엔지니어링 패턴을 심층 분석한다.

## 1. REST 아키텍처의 본질: 로이 필딩의 6대 제약조건

REST는 프로토콜이 아닌 아키텍처 스타일(Style)이다. 특정 분산 시스템이 진정으로 "RESTful"하다고 부르기 위해서는 다음 6가지 제약조건을 시스템적으로 충족해야 한다.

```
REST 6대 아키텍처 제약조건 매트릭스:
┌─────────────────────────┬────────────────────────────────────────────────────────────────────────┐
│ 제약조건                │ 핵심 아키텍처 목적 및 시스템적 효과                                    │
├─────────────────────────┼────────────────────────────────────────────────────────────────────────┤
│ 1. Client-Server        │ 사용자 인터페이스(UI)와 데이터 저장소를 분리하여 독립 진화성 확보      │
├─────────────────────────┼────────────────────────────────────────────────────────────────────────┤
│ 2. Stateless (무상태성) │ 요청 간 세션 상태를 서버 메모리에 저장하지 않음 (수평 확장성 극대화)   │
├─────────────────────────┼────────────────────────────────────────────────────────────────────────┤
│ 3. Cacheable (캐시 가능)│ 모든 응답은 캐시 가능 여부를 명시하여 클라이언트-서버 간 불필요한 왕복 제거│
├─────────────────────────┼────────────────────────────────────────────────────────────────────────┤
│ 4. Uniform Interface    │ 리소스 식별(URI), 표현(JSON), 자기 서술적 메시지, HATEOAS로 결합도 완화│
├─────────────────────────┼────────────────────────────────────────────────────────────────────────┤
│ 5. Layered System       │ 클라이언트는 중간 계층(프록시, 게이트웨이, WAF, 캐시)의 존재를 알 필요 없음│
├─────────────────────────┼────────────────────────────────────────────────────────────────────────┤
│ 6. Code-on-Demand (선택)│ 서버가 클라이언트에 실행 코드(JS 등)를 일시적으로 전송하여 기능 확장   │
└─────────────────────────┴────────────────────────────────────────────────────────────────────────┘
```

특히 **Statelessness(무상태성)**는 클라우드 네이티브 환경에서 수평적 스케일아웃(Auto-scaling)의 절대적인 전제 조건이다. 서버 메모리에 특정 세션이 종속되어 있다면 트래픽을 임의의 백엔드 인스턴스로 분산(Round-Robin)할 수 없기 때문이다. 인증 정보는 JWT나 토큰 형태로 매 요청마다 헤더(`Authorization: Bearer <token>`)에 동봉되어야 한다.

## 2. 리차드슨 성숙도 모델 (Richardson Maturity Model, RMM)

Leonard Richardson은 웹 API가 REST의 원칙을 얼마나 충실히 구현하고 있는지를 4단계(Level 0 ~ Level 3)로 체계화했다.

```
Richardson 성숙도 모델 4단계:
[Level 3: Hypermedia Controls] ──> HATEOAS (응답 내에 다음 가능한 상태 전이 링크 제공)
              ▲
[Level 2: HTTP Verbs]         ──> GET, POST, PUT, DELETE 시맨틱스 및 올바른 상태 코드(201, 404, 409)
              ▲
[Level 1: Resources]          ──> 개별 엔티티마다 독립적인 URI 부여 (/orders/12, /users/45)
              ▲
[Level 0: The Swamp of POX]   ──> 단일 URI (/endpoint), 단일 HTTP 메서드 (POST) 기반 RPC
```

- **Level 0 (The Swamp of POX)**: 단일 엔드포인트(예: `/api/service`)로 모든 요청을 HTTP POST로 전송하고 본문에 메서드 이름과 파라미터를 담는 원격 프로시저 호출(RPC) 형태다. XML-RPC나 단순 JSON-RPC가 이에 해당한다.
- **Level 1 (Resources)**: 단일 엔드포인트 대신 비즈니스 리소스별로 독립된 URI(`/users`, `/orders`)를 도입한다. 하지만 여전히 모든 동작을 POST 하나로만 처리하는 경우가 많다.
- **Level 2 (HTTP Verbs)**: RFC 표준 HTTP 메서드(GET, POST, PUT, DELETE, PATCH)의 시맨틱스를 엄격히 지키고, 그에 부합하는 HTTP 상태 코드(200 OK, 201 Created, 204 No Content, 404 Not Found, 409 Conflict)를 반환한다. **대부분의 엔터프라이즈 프로덕션 API가 위치하는 실용적 목표점이다.**
- **Level 3 (HATEOAS: Hypermedia As The Engine Of Application State)**: 응답 본문 내에 클라이언트가 현재 상태에서 다음에 취할 수 있는 전이 액션들의 URI 링크(`_links`)를 포함시킨다. 클라이언트는 사전 하드코딩된 URI 없이도 서버의 링크를 따라 자율적으로 탐색할 수 있다.

## 3. HTTP 메서드 시맨틱스: 안전성(Safety)과 멱등성(Idempotency)

API 설계 시 가장 많은 버그가 발생하는 영역이 바로 메서드의 멱등성과 안전성 규약을 위반하는 것이다.

```
HTTP 메서드 특성 매트릭스 (RFC 9110 표준):
┌────────┬──────────────────────┬──────────────────────────┬────────────────────────────────────────────┐
│ 메서드 │ 안전성 (Safe)        │ 멱등성 (Idempotent)      │ 주요 용도 및 시맨틱스                      │
├────────┼──────────────────────┼──────────────────────────┼────────────────────────────────────────────┤
│ GET    │ Yes (상태 변경 없음) │ Yes (동일 결과 보장)     │ 리소스 조회 (캐싱 가능)                    │
│ HEAD   │ Yes                  │ Yes                      │ 응답 헤더만 조회 (본문 미포함)             │
│ POST   │ No (서버 상태 변경)  │ No (호출마다 새 리소스)  │ 신규 리소스 생성, 임의의 비즈니스 연산     │
│ PUT    │ No                   │ Yes (전체 대체)          │ 리소스 전체 교체 (없으면 생성 또는 404)    │
│ PATCH  │ No                   │ No (일반적으로 비멱등)   │ 리소스의 부분 수정 (RFC 6902 / RFC 7396)   │
│ DELETE │ No                   │ Yes (삭제 후 상태 불변)  │ 리소스 삭제 (최초 200/204, 이후 404/204)   │
└────────┴──────────────────────┴──────────────────────────┴────────────────────────────────────────────┘
```

- **안전성(Safety)**: 해당 요청을 수행해도 서버의 리소스 상태가 변하지 않아야 한다 (읽기 전용).
- **멱등성(Idempotency)**: 동일한 요청을 한 번 실행하든, 네트워크 재시도로 인해 백 번 실행하든 **서버의 최종 상태가 동일**해야 한다.

### 3.1 분산 환경에서의 멱등성 키(Idempotency-Key) 패턴

결제(`POST /v1/payments`)나 주문 생성과 같이 본질적으로 비멱등(Non-idempotent)한 POST 요청에서, 네트워크 타임아웃으로 인한 클라이언트 재시도 시 중복 결제가 발생하는 것을 방지하기 위해 **Idempotency Key** 패턴을 적용한다.

```
Idempotency-Key 처리 시퀀스:
Client                                           Server / Redis
  │                                                    │
  ├─── POST /payments (Idempotency-Key: uuid-123) ────>│
  │                                                    ├──> Redis SETNX(key, "PROCESSING", ttl=120)
  │                                                    │    - 키 존재 안 함: 결제 PG 연산 수행
  │                                                    │    - 결과를 Redis에 캐싱
  │<── 201 Created (Payment Success) ──────────────────┤
  │
  │ (네트워크 단절로 클라이언트 재전송)
  ├─── POST /payments (Idempotency-Key: uuid-123) ────>│
  │                                                    ├──> Redis GET(key): 이미 처리된 결과 발견!
  │<── 201 Created (캐시된 이전 성공 응답 즉시 반환) ──┤ (PG사 중복 결제 원천 차단)
```

## 4. 실전 URI 및 에러 설계 규약

### 4.1 계층적 복수형 명사 URI 설계
- **명사형 복수(Plural Nouns)**를 기본으로 사용한다: `/orders` (O), `/getOrder` (X).
- 행위는 동사 URI가 아니라 HTTP 메서드로 표현한다: `DELETE /users/12` (O), `POST /users/12/delete` (X).
- 하위 관계는 계층 구조로 표현하되, 2단계를 초과하지 않는다: `/users/{id}/orders` (O), `/companies/{id}/departments/{id}/teams/{id}/members` (X $\rightarrow$ `/teams/{id}/members`로 평탄화).

![URI가 리소스를 식별하고, 표현(Representation)이 그 리소스의 상태를 전달하는 관계](/assets/images/web/official-rest_api.webp)

도식은 URI가 리소스를 식별하고, 표현(Representation)이 메타데이터와 데이터로 그 리소스의 상태를 전달하는 웹 아키텍처의 기본 관계를 보여준다. 출처: Architecture of the World Wide Web, Volume One (https://www.w3.org/TR/webarch/) — W3C Recommendation, W3C Document License(출처 표시 조건부 복사·배포 허용).

### 4.2 RFC 7807 표준 Problem Details 에러 응답
단순히 `{"error": "something failed"}` 형태로 반환하는 것은 클라이언트의 프로그래밍적 에러 분기를 불가능하게 만든다. IETF RFC 7807 표준 에러 포맷을 준수해야 한다.

```json
{
  "type": "https://api.domain.com/errors/insufficient-credit",
  "title": "Insufficient Account Balance",
  "status": 402,
  "detail": "결제 요청 금액(50,000원)이 현재 가용 잔액(12,000원)을 초과했습니다.",
  "instance": "/v1/orders/ord_9981/payment",
  "invalid_params": [
    { "name": "amount", "reason": "잔액 부족" }
  ]
}
```

## 5. 프로덕션 FastAPI 엔지니어링 패턴

FastAPI는 현대 Python 웹 생태계에서 가장 우수한 개발자 경험(DX)과 처리량을 제공하지만, 비동기 런타임의 특성을 이해하지 못하면 심각한 성능 저하가 발생한다.

### 5.1 `async def` vs. 일반 `def`의 스레드 오버헤드 메커니즘

```
FastAPI 엔드포인트 정의별 내부 실행 모델:
[case 1: async def 엔드포인트]
  @app.get("/items")
  async def get_items():
      result = await db.fetch_all()  # 비동기 non-blocking 드라이버 (asyncpg, httpx)
      return result
  * 실행: 단일 uvloop 메인 이벤트 루프에서 직접 실행. 컨텍스트 스위칭 오버헤드가 제로에 수렴하며 수만 QPS 처리 가능.

[case 2: 일반 def 엔드포인트]
  @app.get("/heavy")
  def calculate():
      time.sleep(1)  # 블로킹 I/O 또는 무거운 CPU 연산
  * 실행: FastAPI가 AnyIO 외부 워커 스레드 풀(Threadpool, 기본 40개)에 해당 함수 실행을 위임.
  * 한계: 동시 요청이 40개를 넘어가면 스레드 풀 고갈(Threadpool Starvation)이 발생하여 지연시간이 폭증.
```

> **규칙**: 엔드포인트 함수 내에서 사용하는 모든 I/O 라이브러리가 비동기(`await`)를 지원하면 반드시 `async def`를 선언하라. 반면 레거시 동기 DB 드라이버(`psycopg2`, `requests`)를 사용한다면 차라리 일반 `def`로 선언하여 이벤트 루프 전체가 블로킹되는 재앙을 막아라.

### 5.2 Pydantic V2 기반 엄격한 스키마와 직렬화 가속

FastAPI의 코어 유효성 검증 엔진은 Rust로 재작성된 Pydantic V2를 기반으로 동작한다.

```python
from fastapi import FastAPI, HTTPException, status, Header
from pydantic import BaseModel, Field, ConfigDict
from typing import Annotated
import uuid

app = FastAPI(title="Production Order API", version="1.0.0")

class OrderCreateRequest(BaseModel):
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)
    
    item_id: str = Field(..., min_length=3, max_length=50, description="상품 고유 식별자")
    quantity: int = Field(..., gt=0, le=100, description="주문 수량 (1~100)")
    price_cents: int = Field(..., gt=0, description="단위 가격(센트 단위 정수)")

class OrderResponse(BaseModel):
    id: uuid.UUID
    item_id: str
    quantity: int
    total_price_cents: int
    status: str

@app.post(
    "/v1/orders",
    response_model=OrderResponse,
    status_code=status.HTTP_201_CREATED,
    summary="신규 주문 생성"
)
async def create_order(
    order: OrderCreateRequest,
    idempotency_key: Annotated[str | None, Header()] = None
):
    # 1. 멱등성 검증 로직 수행
    # 2. 비즈니스 로직 및 DB 커밋
    return OrderResponse(
        id=uuid.uuid4(),
        item_id=order.item_id,
        quantity=order.quantity,
        total_price_cents=order.quantity * order.price_cents,
        status="CONFIRMED"
    )
```

## 6. 결론: 계약 중심(Contract-First) API 거버넌스

RESTful API는 우연히 완성되는 것이 아니라, 엄격한 계약(Contract)을 통해 설계된다.

1. **상태 무저장(Statelessness) 유지**: 인스턴스 로컬 메모리에 상태를 보관하지 말고, 완전한 무상태 서버 풀을 구축하라.
2. **시맨틱스 준수**: 안전한 메서드(GET)에서 상태 변경을 일으키지 말고, 멱등성이 필요한 연산(PUT, DELETE)을 정확히 분리하며, 중요한 POST에는 멱등성 키를 적용하라.
3. **비동기 런타임 최적화**: FastAPI 구현 시 `async def`와 비동기 드라이버를 통일하여 uvloop의 처리량을 온전히 누려라.
